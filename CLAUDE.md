# RIZO Service — working notes

After-sales service management for RIZO market (Uzbekistan). Website plus two Flutter apps in the sibling repo `rizo-service-mobile` (RIZO Texnik for technicians / admin / front desk, RIZO Mijoz for customers); technician and customer views must work on phones (360–420px), admin on tablets (768–1024px). `README.md` is the product documentation; this file is the short brief for working in the repo. Keep both current.

## Business rules
- Two service types: **repair** (dead on arrival or failed in use; resolved by repair or replacement; free in warranty, paid otherwise) and **installation** (first-time setup). **No periodic / seasonal maintenance** — never model it.
- Location is **in_shop** or **on_site**, chosen when the request is created. **Installation is always on site at the customer's address** (in-shop installation is not allowed; the API rejects it). Repairs can be either. On-site needs an address (+ optional lat/lng).
- `source` is `rizo_service` | `rizo_market`. Request creation lives in service-layer code so a future RIZO market API can call it. The RIZO market posts sales to `POST /api/integrations/market/sales` (`X-Api-Key` = `MARKET_API_KEY`).
- Warranty runs from the **installation date** when the product was installed (set when an installation request completes), otherwise from the sale date. Dates are UTC date-only; "today" is `Asia/Tashkent`.
- Cost: 0 if in warranty (extras are still charged), otherwise services + parts + extra expenses. Profit = revenue − part **cost price** (snapshotted per line) − extra expenses.

## Roles
`admin` (dispatcher), `receptionist` (front desk: board, requests, customers, sales, calendar, map, part orders, kiosk — no reports/settings/staff/catalog), `technician` (`mobile` | `service_center`), `accountant` (reports, payroll, fiscal/partner reports; read-only elsewhere), `warehouse` (spare parts, part orders, technician stock), `customer`. Role sets live in `server/src/lib/roles.ts`; use `readWriteRoles(read, write)` for routes where reads are wider than writes. Staff and customers both sign in with phone + password; customers get a separate JWT scope. Reports, dashboard, inventory, schedule, audit, duplicates, staff admin and settings changes are admin-only **at the API** (`requireStaffRole("admin")`). Customer queries are always scoped to the token's customer id. Deactivated staff (`is_active=false`) cannot sign in and lose API access within ~15s.

## Status model (one model for both types, per `Rizo.xlsx` #4)
`new → diagnosing → awaiting_decision → awaiting_parts → in_progress ⇄ paused → ready | completed | replaced → picked_up`, plus `refunded`, `rejected`, `cancelled`. Installation is `new → in_progress → completed` (+ paused/cancelled). Tables live in `server/src/lib/status.ts` (mirrored in `client/src/lib/status.ts`); the technician board folds them into 4 columns (`lib/techBoard.ts`).
- Repair flow: diagnose → **decision** (warranty_repair / paid_repair / replace / refund / reject, reject needs a reason) → paid repair needs an **approved estimate** (setting `require_estimate_for_paid_repair`) → part shortage creates a **PartOrder** and `awaiting_parts` → completion (`ready` in shop, `completed` on site, `replaced`).
- Timers: New 1 day, In progress 3 days, Paused = technician-set hours, awaiting_* from `status_changed_at`. A pause **requires a reason**.
- Pickup only follows `ready`/`completed` for in-shop jobs and is blocked while a balance is unpaid (staff can pass `allowUnpaid`).
- Completion needs ≥1 photo, a service when the category has any (not for replacements) and — for replacements — the new product + serial.
- All transitions go through `server/src/lib/statusChange.ts` (`changeRequestStatus`); decisions through `lib/decision.ts`, estimates `lib/estimates.ts`, payments `lib/payments.ts`, part orders `lib/partOrders.ts`, pickup `lib/pickup.ts`, request creation (staff + portal) `lib/createRequest.ts`.
- Rules (AppSetting): `repair_warranty_days` 30, `repair_legal_days` 20, `estimate_valid_days` 7, `pickup_storage_days` 14. Repeat failure = same serial within 12 months; duplicate open request → 409 `duplicateRequest`.
- Public (no login) tracking: `/t/:token` and `/track` (request number + phone, rate limited); service centers at `/centers`.
- The Telegram bot starts only when `TELEGRAM_BOT_TOKEN` is set and the provider is not `console` (webhook when `TELEGRAM_WEBHOOK_URL` + `TELEGRAM_WEBHOOK_SECRET` are set, else long polling).

## Conventions
- **i18n**: Uzbek default, Russian, English. No hardcoded UI strings; add keys to all three locale files. Server errors are English with a `code`; the client maps `errors.<code>`. Add new messages to `MESSAGE_CODES` in `server/src/middleware/error.ts` (or throw `HttpError` with an explicit code). `audit.action.*` keys are flat dotted keys (`"request.status"`) — never nest them next to each other or i18next stops resolving the flat ones. Run `node server/scripts/i18n-scan.mjs` — `portal.pendingFeedback` / `portal.photoCount` show as "missing" only because they are plural keys.
- **Request ID** `display_id` = `DDMMYY` (Tashkent) + 2-digit region + 4-digit daily sequence (one counter per day, atomic upsert), shown as `#…`.
- **Brand**: purple `#7B00E0`, orange `#F7941E` as accents on a light neutral base (never a full purple screen). Staff app = white header; customer portal = purple-tint header with orange rule and badge. Logo: `client/public/rizo-logo.svg` (do not redraw it).
- **One website sign-in** (`/login`, `POST /api/auth/login`, `features/auth/LoginPage.tsx`): staff and customers use the same form; the answer for a wrong phone or password never says which side a number belongs to. The apps stay separate (RIZO Texnik / RIZO Mijoz) and keep `/api/staff/auth/login` and `/api/customer/auth/login`, which answer 403 `useCustomerApp` / `useStaffApp` when the password is right for the other side. **Two sides, one at a time**: a staff sign-in and a customer sign-in clear each other's token. While one side is signed in, the other side's entrances are not shown: the public pages' top-right button (`BrandChrome`) and the home page offer only the way back to the signed-in side, `/login` redirects to it, and the portal has its own `/portal/centers`. The last phone used on each side is remembered in `localStorage` (`lib/lastAccount.ts`, never the password) and prefilled with an "other account" link.
- Requests are never hard-deleted. Everything audit-worthy goes through `writeAudit`.
- Stubs that are not real integrations: SMS and Telegram default to a `console` driver (set `SMS_HTTP_URL` / `TELEGRAM_BOT_TOKEN` to send). Password-reset SMS therefore only appears in the API log until a gateway is configured.

## Spare-part control (added 2026-10)
`lib/partsControl.ts` (waiting jobs, per-part metrics and recommendations, `receivePartOrder`, `runPartsWatch` called from `runHousekeeping`), `routes/partOrders.ts` + `routes/suppliers.ts`, models `Supplier` and `SparePart.supplierId/targetStock`, `PartOrder.supplierId/orderedAt/lateNotifiedAt`. Receiving always goes through `receivePartOrder` (it releases every waiting job, not only the linked one). Shortage is judged **per part** (needs − stock − all open orders), not per job. Staff alerts take `roles` (`notifyAdmins({ roles: ["admin","warehouse"] })`) and `notifyStaffUser` for one person. Notification codes `partOrdered partEta partLate partWaiting partOrderLate partNoOrder reorderSuggestion jobPartReady` live in the website and mobile locales (`notify.*`); after adding codes run `node server/scripts/sync-push-texts.mjs`. Check: `npm run smoke:parts -w server`. The customer-facing wait is `customerPartWait` (`partWait` on portal and public tracking payloads). The admin dashboard payload carries `parts` (= `partsOverview()`). Mobile: `apps/rizo_staff/lib/parts/` (the same four views), warehouse role signs in to the staff app; models in `rizo_core` (`WaitingRequest`, `RecommendationGroup`, `SupplierInfo`, `PartsOverview`, `PartWait`). Demo loader/cleaner handle suppliers, `DEMO ` parts and their orders.

## Warehouses (added 2026-10)
Central / regional / branch warehouses (`Warehouse`, `PartStock` per shelf, `StockTransfer` between them, `StaffUser.warehouseId`, `PartOrder.warehouseId`); `SparePart.stockQuantity` is the total of the shelves, so **never write it directly: go through `lib/warehouses.ts`** (`addStock` / `takeStock` / `setStock`; the catalogue form uses `setTotalViaCentral`). A job takes parts from `homeWarehouseId` (technician's warehouse → their centre's stock room → regional → central). `rankSources` ranks where a part can come from by delivery days (warehouse lead days, same / other region, minus what is already promised) against the supplier; `partSourcing.sourceMissingPart` picks (or takes the chosen) source for a job; `transfers.ts` runs request → ship (partial) → receive (partial returns the rest) / reject (re-routes a job-linked request) / cancel and the watch (`runTransferWatch` from housekeeping). Access is in `warehouseAccess.ts` (keeper with `warehouseId` manages only that one). Notification codes `transferRequested transferShipped transferRejected transferStale transferLate warehouseLow`. Website `features/warehouses/` (+ technician dialogs on the job page and My stock), mobile `apps/rizo_staff/lib/warehouse/` and `tech/part_request_sheet.dart`. Check: `npm run smoke:warehouses -w server`. Demo: 8 warehouses + requests (loader marks them `DEMO-DATA`, cleaner removes them).

## Telegram bot (added 2026-10)
`server/src/lib/telegram/` (`index.ts` routing + webhook/polling, `customer.ts` menu, requests, new-request dialogue, warranty, centres; `staff.ts` alerts; `links.ts` one-time keys and linking; `text.ts` every string in uz/ru/en; `api.ts` Bot API + a test stub via `setTelegramCaller`). `lib/telegramBot.ts` only re-exports. ## Automatic tasks (added 2026-10-12)
`lib/autoJobs.ts` owns four jobs: `deadline_watch` (every minute; warns the technician once per job and timer when `deadline_warning_percent` of the time is left or the legal limit is `legal_warning_days` away; admins get one summary), `daily_report`, `weekly_digest`, `payroll_statements` (stored in `payroll_statements`, one row per technician and period, upserted). Each run is logged in `auto_job_runs`; `tickAutoJobs()` (index.ts, every minute) also **catches up** a missed slot after the server slept (a first-ever run is only allowed within 12 h of its slot). Admin page `/app/automation` (accountant reads) has a **Run now** button per job (`POST /api/staff/auto-jobs/:key/run`); technicians read their own statements at `GET /api/staff/auto-jobs/my-statements`. Mobile: admins open it in RIZO Texnik under More → Automatic tasks (`apps/rizo_staff/lib/admin/automation_screen.dart`, same API; widget test `test/automation_test.dart`). In app code never call `context.tr` / `context.errorText` inside event handlers (they `watch`; use `tr(...)` / `Translator.I.errorMessage`). Tests: `npm run smoke:auto -w server`.

## Brands, models of other makers and the queue rule (added 2026-10)
The system also repairs devices of **other makers** (a master's own customers, not only RIZO market). `Brand` (the company's own is `brand_rizo`, `isOwn`; every product has a `brandId`, default RIZO) and `Product` rows under other brands (`sku EXT-…`, **no RIZO warranty**, repair always paid). `lib/brands.ts` normalises names (`directoryKey`: letters and digits only, so "Samsung" = "SAM-SUNG"), refuses near-duplicates with a 409 `similarBrand` / `similarModel` unless `force`, and `usableProductWhere` / `assertUsableProduct` keep unapproved models out of requests. **Who adds**: technicians, front desk and admins (`routes/directory.ts`, `/api/staff/directory/*`); only an admin's own entry is approved at once, everyone else's waits for **one admin** to approve (`catalogPendingBrand|Model` alert); admins also rename, merge (moves models, requests, skills) and delete. **Customers never add anything**: the customer app, portal and sale registration list and accept RIZO products only. Technicians keep an "I repair" list (`StaffSkill`: a whole brand or one model; what they add themselves lands in it); admins edit it on the Staff page / in the app. **Queue rule** (`lib/queue.ts`): first tier = RIZO product or any job under warranty; second tier = another maker, paid. A second-tier job goes only to a technician who lists it (`pickAvailableTechnician(…, { secondTier })`, free technicians first) and its technician cannot start it (status change, en route, any edit via `loadOpenJob`) while they have first-tier jobs in New, Diagnostics or In progress (409 `waitingForWarranty`; paused / waiting for parts do not block). An admin may move one to the front with a reason (`POST /requests/:id/queue-override`, audited, `queueOverride*` columns). Serialized requests carry `tier`, `brand`, `queueOverride`; the technician list and the request page carry `waitingForFirstTier` / `queue`. Website: `features/directory/` (Directory page, "I repair" page, `OtherDevicePicker` on the new-request page, `QueueNotice`); apps: `apps/rizo_staff/lib/directory/`. Check `npm run smoke:brands -w server`; the demo loader adds Samsung / LG / Artel / Bosch, one pending Midea model, skills and four second-tier requests (all noted `DEMO-DATA`, removed by the cleaner).

## Staying signed in (added 2026-10)
Sessions last 30 days (`JWT_EXPIRES_IN`) and **slide**: `GET /api/{staff|customer}/auth/me` returns a fresh `token` when the one sent is older than 12 hours (`lib/jwt.ts` `renewedToken`, built from the account's current role/name/phone). The website keeps it in localStorage for the next visit (`*AuthContext.tsx`), the apps in secure storage (`AuthSession.restore`). A deactivated staff member still loses access within ~15 s. If production sets `JWT_EXPIRES_IN` explicitly, that value wins over the default. Check: `npm run smoke:auth -w server`.

## Lists, tables and the site's security headers (added 2026-10)
- **Paging**: `GET /api/staff/requests|customers|sales` take `limit` (1–200) and `offset` and always answer `total` + `hasMore`; without `limit` they return up to 1000 rows (calendar, map, receipts, the board and the mobile apps rely on that). Screens use `usePagedList` + `<LoadMore>` (50 per page).
- **Tables**: always use `SurfaceTable` / `Th` / `Td`. Below `md` it turns into one card per row by itself (column names come from the header row), so never add a separate phone layout and never let a table scroll sideways.
- **Payments are whole so'm** (`amount` integer, max 9 999 999 999).
- **CSP** lives in `netlify.toml`. It allows the site itself, Google Fonts, OpenStreetMap tiles and the API (https + wss). If the inline theme script in `client/index.html` changes, update its sha256 in the policy; if the API host changes, update both occurrences. Test a change by serving `client/dist` with the same header and watching the console for "Refused to …".

## Demo data (added 2026-10)
`npm run demo:load -w server` fills a database with ~150 served customers (sales, installations, repairs in every status, payments and debts, photos, customer ratings, spread over ~5 months); `npm run demo:clean -w server` removes exactly that again. The loader uses the real API (so every rule holds) and then moves timestamps into the past with SQL; it needs `API`, `DATABASE_URL` and the logins of an admin, a receptionist and one mobile + one service-centre technician (`DEMO_ADMIN`, `DEMO_DESK`, `DEMO_TECHS`, defaults are the seed accounts). Customers carry the note `DEMO-DATA` (password `Demo12345`), extra products the SKU prefix `DEMO-`. A non-local database needs `DEMO_CONFIRM=yes`. Photos are code-drawn illustrations (`server/scripts/demo/images.ts`). Never run it against a database that holds real customers unless the demo is meant to be there: requests cannot be deleted inside the app, only by `demo:clean`.
